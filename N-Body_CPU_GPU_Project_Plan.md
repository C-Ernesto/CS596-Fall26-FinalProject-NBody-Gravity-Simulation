# CPU–GPU Performance Analysis and Optimization of an N-Body Gravitational Simulation

## 1. Project overview

This project will implement the same gravitational N-body simulation using four execution strategies:

1. Serial CPU
2. Parallel CPU with OpenMP
3. Naïve GPU with CUDA
4. Optimized GPU with CUDA shared-memory tiling

The goal is to determine how problem size and implementation strategy affect performance, while verifying that all implementations produce scientifically valid results.

### Main objective

> Implement and evaluate serial, OpenMP, naïve CUDA, and tiled CUDA versions of a direct N-body simulation, then identify when CPU or GPU execution is most effective.

### Assumptions

- Language: C++
- CPU parallelism: OpenMP
- GPU parallelism: CUDA
- Platform: USC CARC Discovery cluster
- Hardware scope: one compute node and one NVIDIA GPU
- Algorithm: direct all-pairs gravitational force calculation, O(N²)
- Numerical method: velocity Verlet
- Project length: approximately 6–10 weeks
- MPI, multiple nodes, and multiple GPUs are outside the core scope

## 2. Research questions

- **RQ1:** How well does the OpenMP implementation scale as the number of CPU threads increases?
- **RQ2:** At what number of bodies does the GPU become faster than the serial and OpenMP implementations?
- **RQ3:** How much faster is a shared-memory tiled CUDA kernel than a naïve CUDA kernel?
- **RQ4:** What portion of GPU execution time comes from computation versus CPU–GPU memory transfers?

### Expected hypotheses

- OpenMP will outperform serial execution for medium and large particle counts.
- GPU execution may be slower for small particle counts because of launch and transfer overhead.
- CUDA will outperform OpenMP once the problem is sufficiently large.
- Shared-memory tiling will reduce global-memory traffic and improve performance over the naïve CUDA kernel.

## 3. Scientific model

Each body has a position, velocity, mass, and acceleration. A simple initial structure is:

```cpp
struct Body {
    double x, y, z;
    double vx, vy, vz;
    double mass;
};
```

Separate arrays may later be used to improve GPU memory access:

```cpp
double* x;
double* y;
double* z;
double* vx;
double* vy;
double* vz;
double* mass;
```

### Force calculation

For every body i, calculate the acceleration generated by every other body:

\[
\mathbf a_i =
G\sum_{j\ne i}
m_j
\frac{\mathbf r_j-\mathbf r_i}
{\left(\|\mathbf r_j-\mathbf r_i\|^2+\epsilon^2\right)^{3/2}}
\]

The softening parameter epsilon prevents an extremely large force when two particles become very close. Normalized units can be used, with G = 1 and equal particle masses.

### Velocity Verlet integration

1. Compute the initial acceleration.
2. Update position:

\[
\mathbf r_i(t+\Delta t)=
\mathbf r_i(t)+\mathbf v_i(t)\Delta t+
\frac{1}{2}\mathbf a_i(t)\Delta t^2
\]

3. Calculate acceleration at the new position.
4. Update velocity:

\[
\mathbf v_i(t+\Delta t)=
\mathbf v_i(t)+
\frac{1}{2}\left[\mathbf a_i(t)+\mathbf a_i(t+\Delta t)\right]\Delta t
\]

All four implementations must use the same initial conditions, time step, softening value, precision, and integration method.

### Phase 2: Serial CPU implementation

Implement the complete velocity-Verlet simulation using a serial nested loop:

```cpp
for (int i = 0; i < N; ++i) {
    ax[i] = ay[i] = az[i] = 0.0;

    for (int j = 0; j < N; ++j) {
        if (i == j) continue;
        // Calculate acceleration contribution from body j.
    }
}
```

Add calculations for:

- Kinetic energy
- Potential energy
- Total energy
- Total linear momentum
- Center of mass

**Deliverable:** A correct serial simulator that passes force and two-body tests.

### Phase 3: OpenMP implementation

Parallelize the outer force loop:

```cpp
#pragma omp parallel for schedule(static)
for (int i = 0; i < N; ++i) {
    // Compute acceleration for body i.
}
```

Each thread owns different target bodies, so the primary force loop should not require locks or atomics.

Test thread counts:

```text
1, 2, 4, 8, 16, 32
```

Use only thread counts supported by the CARC allocation. Suggested environment settings are:

```bash
export OMP_NUM_THREADS=$SLURM_CPUS_PER_TASK
export OMP_PROC_BIND=true
export OMP_PLACES=cores
```

**Deliverable:** An OpenMP version that agrees with the serial version and produces a CPU scaling graph.

### Phase 4: Naïve CUDA implementation

Assign one GPU thread to each target body:

```cpp
__global__
void compute_acceleration_naive(
    const double* x,
    const double* y,
    const double* z,
    const double* mass,
    double* ax,
    double* ay,
    double* az,
    int N
) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= N) return;

    for (int j = 0; j < N; ++j) {
        // Calculate contribution from body j.
    }
}
```

Implementation order:

1. Allocate GPU memory.
2. Copy initial particle data to the GPU.
3. Run all simulation steps on the GPU.
4. Copy final positions and velocities to the CPU.
5. Free GPU memory.

Keep the simulation state on the GPU instead of copying it after every step. Test CUDA block sizes 64, 128, 256, and 512.

**Deliverable:** A correct basic CUDA version and an initial CPU-versus-GPU performance graph.

### Phase 5: Shared-memory tiled CUDA implementation

Divide the source particles into tiles:

1. Each thread loads one source particle into shared memory.
2. Synchronize the block.
3. Every thread calculates interactions with particles in the tile.
4. Synchronize again before replacing the tile.
5. Repeat until all source particles have been processed.

This allows particle data loaded from global memory to be reused by multiple threads.

**Deliverable:** A tiled CUDA implementation that agrees with the serial result and can be compared directly with the naïve CUDA kernel.

## 6. Correctness and validation

### Test A: Small force calculation

Use 2–10 particles with known positions. Compare acceleration results from all implementations using a relative tolerance:

\[
\frac{|a_{parallel}-a_{serial}|}
{\max(|a_{serial}|,\delta)} < \tau
\]

For double precision, begin with a tolerance around 10^-9 or 10^-10 and adjust only if justified.

### Test B: Two-body orbit

Simulate two equal masses orbiting their center of mass. Verify that:

- The bodies remain bounded.
- The center of mass remains nearly fixed.
- Total momentum remains nearly constant.
- Total energy does not drift rapidly.

### Test C: Short-run implementation agreement

Run every implementation using the same seed with N = 128 for 10–20 steps. Compare positions against the serial implementation using RMSE:

\[
RMSE =
\sqrt{\frac{1}{N}\sum_{i=1}^{N}
\|\mathbf r_i^{parallel}-\mathbf r_i^{serial}\|^2}
\]

Use short runs for direct position comparison. N-body systems can be chaotic, so small floating-point differences may grow during long runs even when both implementations are correct.

### Test D: Conservation measurements

Calculate relative energy drift:

\[
\frac{|E(t)-E(0)|}{|E(0)|}
\]

Also monitor the change in total linear momentum.

## 7. Benchmark design

### Particle counts

Begin with:

```text
256, 512, 1024, 2048, 4096, 8192, 16384
```

Add 32768 only if its runtime is manageable. Because the direct algorithm is O(N²), doubling N creates approximately four times as many interactions.

### OpenMP thread counts

```text
1, 2, 4, 8, 16, 32
```

### CUDA block sizes

```text
64, 128, 256, 512
```

Tune block size using a few representative particle counts, then use the best block size for the main comparison.

### Repetitions

- Perform one warm-up run.
- Perform at least five measured runs.
- Report the median runtime.
- Record variability using the minimum and maximum or standard deviation.

### Fairness controls

- Run CPU and GPU tests on the same GPU-node type when possible.
- Use a fixed seed and identical initial conditions.
- Use identical numerical precision and compiler optimization levels.
- Disable file output and visualization during timed regions.
- Record CPU model, GPU model, compiler version, CUDA version, flags, Slurm job ID, and experiment date.
- Do not combine measurements from different GPU models into one performance curve.

## 8. Timing methodology

### CPU timing

Use `omp_get_wtime()` for both serial and OpenMP execution.

### GPU kernel time

Use CUDA events around the kernels and synchronize before reading the result.

### End-to-end GPU time

Separately measure:

- GPU allocation
- CPU-to-GPU input transfer
- Kernel execution
- GPU-to-CPU result transfer

Report both kernel-only and end-to-end GPU results. Use end-to-end time when determining the real CPU–GPU crossover point.

## 10. Performance metrics

### OpenMP speedup

\[
S_P = \frac{T_1}{T_P}
\]

### OpenMP efficiency

\[
E_P = \frac{S_P}{P}
\]

### GPU speedup

\[
S_{GPU} = \frac{T_{best\ OpenMP}}{T_{GPU}}
\]

### Interaction rate

\[
Interactions/second =
\frac{N(N-1)\times steps}{execution\ time}
\]

### GPU crossover point

The crossover point is the smallest N for which:

\[
T_{GPU,total} < T_{OpenMP}
\]

Use end-to-end GPU time for this conclusion.
